# 确定性读取与计算下沉脚本，散文只留判断

凡是能确定性完成的读取与计算（取数、匹配、归组、排序、比对、生成候选），一律做成 `vendor.mjs` 的只读查询或其固定输出模板，产出机器可转述的证据；SKILL.md 的散文只保留三类内容：需要判断或取舍的规则、需要用户提供或确认的取值、以及安全/凭据边界。门禁类检查（ordering、drift、exact sync 断言）必须有机器产物，AI 的任务是运行、原样转述、并据输出向用户提问，而不是用自然语言断言结论。

触发实例：会话 `01a0cc2c` 中模型排序门禁只有散文，AI 用「我没移动位置」一句断言放过了真实乱序（`claude-opus-5-5` 09-22 排在 `claude-fable-5-1` 09-01 之前）；同一条链路的 exact sync 与 drift 因为都有机器输出而未被绕过。修正见 `byissue/issues/096-x-vendor-machine-ordering-audit.md`。

## 背景与取舍

- 备选一：把排序逻辑写成 SKILL.md 内的固定 Node 模板（仿 exact sync 的 Generate the plan）。否决理由：这仍是同一条临时逻辑换地方放，SKILL 继续增重，且难以 fixture 单测；脚本子命令可进 `vendor-script.test.ts`、可复用、可 `--help` 式发现。
- 备选二：保持散文、只加强措辞。否决理由：本次失败证明无产物的门禁可被自我说服绕过。
- 代价：AI-facing 只读查询从三个变四个，脚本面变大。这是有意为之——只读、无凭据、不出网、可单测，风险低于把确定性判断留给模型。脚本保持「不出网」：需要外部数据（models.dev）时由调用方取好文件再传入。
- 边界：写操作仍归 AI 的 `edit`，脚本不出写动词；用户的取舍（来源、目标 provider、是否重排）不由脚本裁决，脚本只给出机器事实与候选顺序。
